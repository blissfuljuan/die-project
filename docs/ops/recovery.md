# Backup, recovery and incident runbook (P0-VS05)

Read [deployment.md](deployment.md) first for the topology. Commands marked *(run)* were executed against the Compose stack while writing this document;
commands marked *(not run)* depend on Render or Supabase, which this repository has not been deployed to.

## 1. What holds the truth

| Data | Authoritative store | Lost if... | Recovery source |
|---|---|---|---|
| Accounts, classes, projects, audit log, job and outbox state, sessions | **Postgres (Supabase)** | the database is lost | Postgres backups (section 2) |
| Messages in flight | RabbitMQ (transport only) | the broker disk is lost | Postgres outbox + resubmission (section 5) |
| Topology (exchanges, queues, DLQs) | `infra/rabbitmq/definitions.json` in git | never lost | re-import (section 5) |
| Configuration | `render.yaml`, `docker-compose.yml`, `.env.example` in git; secret values in your password manager | the dashboard is wiped | git + password manager (section 3) |
| Student documents (P2) | **the owner's Google Drive** (not our copy) | the Drive file is deleted | Drive's own trash/versions, not DIE |
| Artifact manifest (P2) | Postgres (storage references, checksums) | with the database | Postgres backups; **see the note in section 4** |

Workers hold no state. Sessions are server-side rows in Postgres: there are no signing keys to rotate.

## 2. Postgres backups

Two layers; use both, neither replaces the restore test.

1. **Provider backups**: Supabase's automatic daily backups and point-in-time recovery depend on the plan (free plans have none; check *Database > Backups* in your project). *(not run)* They live in the same provider account as the database, so they do not protect against losing the account.
2. **Your own logical dump to storage you control** (`scripts/backup-postgres.sh`, *run*): `pg_dump --format=custom`, schema `public`, with privileges, without owners, plus a SHA-256 file.

   ```bash
   BACKUP_DATABASE_URL='postgresql://die_migrator.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres?sslmode=require' \
   BACKUP_DIR=./backups scripts/backup-postgres.sh
   ```
   * The `pg_dump` major version must be >= the server's (`PG_IMAGE=postgres:17-alpine`). Use the schema owner or a dedicated read-only role, never `die_app`.
   * Run it at least daily from a machine or scheduler you control (cron, a laptop task, any CI that holds the secret). The repository's CI deliberately has no secrets, so it does not run backups.
   * Encrypt before it leaves the machine (`age -r <public key>` or `gpg -c`), copy to **object storage in a different account/provider**, keep 30 dailies + 12 monthlies, and keep the decryption key somewhere other than the backup.
   * Measured: the dump of a freshly migrated development database is about 60 KB; real size grows with audit and job history.

What a dump does **not** contain: the roles and their passwords (cluster objects), RabbitMQ data, Google Drive files, Render and Supabase settings.

## 3. Configuration backup

* Everything non-secret is in git: `render.yaml`, Dockerfiles, RabbitMQ definitions, migrations. A fresh Render Blueprint apply recreates the services from it.
* Secrets are *names* in git (`sync: false`) and *values* in your password manager. Keep one entry per variable listed in deployment.md section 3 (DB URL and the two role passwords, SMTP credentials, `DIE_FRONTEND_BASE_URL`; the broker password is generated by Render: copy it once from the env group if you need to connect by hand).
* After any dashboard change that is not in git (plan, region, custom domain, env value), update `render.yaml` or the password manager entry in the same sitting. Export the current Render env var *names* with the dashboard's "Download .env" action only into the password manager, never into git.
* RabbitMQ users and passwords are not in `definitions.json` by design.

## 4. Artifact manifest is not a file backup

From P2 on, Postgres records for each submitted artifact where it is stored (Drive file id, version, checksum, who/when): a **manifest**. A manifest tells you *which* files should exist and lets you detect a missing or altered file; it cannot recreate one. The documents themselves stay in the instructor's/project's Google Drive (or the S3-compatible store added later) and are protected only by that service's trash, version history and retention. Therefore:

* Do not describe a database backup as a document backup to stakeholders.
* If a Drive file is deleted, recovery is Drive's trash (usually 30 days) or the participant resubmitting; DIE can only report the mismatch.
* When P2 lands, add a periodic "manifest vs Drive" verification job and an export of the manifest to the backup set. (Not implemented yet: there are no artifacts today.)

## 5. RabbitMQ

### 5.1 Re-import the topology

The topology is idempotent and is imported on every broker start by `infra/rabbitmq/die-entrypoint.sh`, so restarting the broker repairs missing exchanges/queues. To import by hand:

```bash
docker compose exec rabbitmq rabbitmqctl import_definitions /etc/rabbitmq/definitions.json        # Compose (run)
# Render: dashboard > die-rabbitmq > Shell > rabbitmqctl import_definitions /etc/rabbitmq/definitions.json    (not run)
```
To compare the live broker with git, `rabbitmqctl export_definitions /tmp/live.json` and diff it against `definitions.json` (users and permissions will appear only in the export).

### 5.2 Dead-letter queues: inspect and replay

Messages that exhausted their retries or were malformed land in `<queue>.dlq` with headers `x-die-failure-reason` and `x-die-source-queue`. DLQs are never consumed automatically. *(run, `scripts/dlq.py`, management API on `RABBITMQ_MGMT_URL`)*

```bash
export RABBITMQ_MGMT_URL=http://127.0.0.1:15672 RABBITMQ_USER=... RABBITMQ_PASSWORD=...
python3 scripts/dlq.py list                                   # which queues hold messages
python3 scripts/dlq.py peek die.test.analyze.dlq              # show messages, removes nothing
python3 scripts/dlq.py replay die.test.analyze.dlq --count 1 --reset-attempt
```
Rules:
1. **Find the cause first** (`x-die-failure-reason`, the worker logs for the `correlationId`). Replaying before the fix only refills the DLQ.
2. `replay` publishes the message back to its source queue (convention: domain = first two name segments, see messaging.md section 2), keeps `messageId`/`correlationId`, and removes the DLQ copy only after the broker accepted the new one. Consumers dedupe on `messageId`, so a crash in between cannot process it twice.
3. `--reset-attempt` gives the message the full retry budget again (otherwise a message that already used 3 attempts gets one more try). Verified: a replayed message went through retry tiers 1 and 2 again.
4. A body that is not valid JSON is never replayed by the script. Read it with `peek`, decide, and discard through the management UI (*Queues > the DLQ > Get messages / Purge*). Never purge a DLQ you have not read.
5. A job that is already `FAILED` in Postgres stays failed after a replayed result (terminal states never change); resubmit the job instead.

Without the management port (Render): use `rabbitmqctl list_queues name messages` in the service shell to see counts; to move messages enable the shovel plugin (`rabbitmq-plugins enable rabbitmq_shovel`) and define a one-off dynamic shovel from the DLQ to the work exchange *(not run)*.

### 5.3 Broker disk loss

1. Start a new broker with an empty disk (Render: delete the disk contents or create a new disk; the `RABBITMQ_USER/PASSWORD` seed the login again).
2. The entrypoint imports the topology; confirm with `GET /api/v1/ops/health` (broker UP, queue depths 0) and `/actuator/health/readiness`.
3. Reconcile jobs: outbox rows still `PENDING` publish by themselves. Rows already `PUBLISHED` whose jobs never finished are failed by the stale-job reaper after `DIE_OPS_STALE_JOB_SECONDS`; resubmit those jobs. To speed this up, lower the threshold temporarily or fail them by hand (section 7).
4. Run the smoke test.

### 5.4 Credentials

`RABBITMQ_DEFAULT_*` only seeds an empty broker. To change the password of a running broker: `rabbitmqctl change_password die '<new>'`, then update the env group (`die-broker`) and restart the API and both workers. Restarting the broker alone does not apply a new password.

## 6. Restarting workers and the API

Workers are stateless and idempotent; restarting them is always safe. A message being processed when the worker dies is redelivered (manual acks).

| Environment | Command |
|---|---|
| Compose | `docker compose restart orchestrator document-worker` (*run*: with the orchestrator stopped, `GET /api/v1/ops/health` reported it `UNREACHABLE` and `DEGRADED`; after start it was `UP` again) |
| Render | dashboard > service > *Manual Deploy > Restart service* (*not run*) |

How to tell a worker is unhealthy: `workers[]` in `GET /api/v1/ops/health` (`state` UP/DOWN/UNREACHABLE and `heartbeatAgeSeconds`; a heartbeat older than 90 s is stale), container health in `docker compose ps`, or the worker's `/health/ready`. DOWN with a fresh heartbeat usually means "not consuming": the broker is down or unreachable (verified by stopping RabbitMQ). Restart the broker first, then workers only if they do not recover on their own within a minute.

## 7. Stale test jobs

The reaper (`StaleJobReaper`, every 60 s on every API instance, safe in parallel through `FOR UPDATE SKIP LOCKED`) fails test jobs that were `QUEUED` or `RUNNING` for longer than `DIE_OPS_STALE_JOB_SECONDS` (900), sets `failure_reason`, and writes an audit row `TEST_JOB_REAPED` (no actor). A result that arrives later is ignored. `GET /api/v1/ops/health` shows `testJobs.overdue` (jobs past the threshold that the reaper has not yet handled). Manual equivalent (as the schema owner):

```sql
UPDATE test_job SET state='FAILED', failure_reason='failed by an operator: <why>', finished_at=now(), updated_at=now()
WHERE id = '<id>' AND state IN ('QUEUED','RUNNING');
```
Evaluation jobs (P3) will use leases and fencing instead; this reaper does not cover them.

## 8. Rolling back a deployment and migrations

* **Application rollback**: Render dashboard > service > *Events > Rollback* to the previous successful deploy (API, workers, frontend each separately) *(not run)*. Compose: `git checkout <tag>` and `docker compose up -d --build`.
* **Migrations are forward-only.** Never edit an applied migration (CI blocks it) and do not run `flyway repair` without reading what it will change. A rollback of the application therefore must keep working with the *newer* schema. Rule for authors: **expand, then contract** over two releases: release N adds the column/table (nullable or defaulted, old code ignores it); release N+1 starts using it; only release N+2 removes or tightens anything the old code still needs. A migration that cannot satisfy this (drop, rename, type change) needs a maintenance window and a fresh backup immediately before it.
* **If a migration failed half way**: Flyway runs each migration in a transaction on PostgreSQL, so a failed one leaves no partial change; the API refuses to start and the old release keeps running on Render. Fix forward with a new migration number.
* **If a bad migration was applied**: restore from the backup taken before the deploy (section 9) into a new database, or ship a corrective `V<n+1>` migration. Do not edit history.
* Take a `scripts/backup-postgres.sh` dump before every release that contains a migration.

## 9. Restoring Postgres

### 9.1 Restore test (routine, monthly and after changing the backup process)

Proves a dump is restorable and usable, without touching production. *(run against a real dump of the Compose database)*

```bash
scripts/restore-test.sh backups/die-<timestamp>.dump
```
It verifies the checksum, starts a throwaway `postgres:16-alpine`, creates the `die_app` role, runs `pg_restore --clean --if-exists --no-owner`, and checks: Flyway history ends at the latest migration in the repository and has no failed entries; prints row counts of the key tables (compare them with the source: `SELECT count(*) ...` on production for `app_user`, `audit_log`, `project`); `die_app` can read; `die_app` cannot delete `audit_log` rows. It prints `RESTORE TEST PASSED` and removes the container.
Record each run: date, dump file and checksum, who ran it, row counts, result. A backup that has never been restored is not a backup.

### 9.2 Real restore

1. Decide the target: a **new** Supabase project/database (preferred: the old one stays available for forensics) or the same database after taking a fresh dump of its current state.
2. Create the roles with the SQL from deployment.md section 4 (passwords may be new).
3. Stop writers: scale the API to zero / suspend `die-api` and the workers so nothing writes while restoring.
4. Restore as the schema owner: `pg_restore --clean --if-exists --no-owner --role=die_migrator --dbname '<url>' die-<timestamp>.dump`. (`--clean` drops what exists in schema `public`: only point it at the database you mean to overwrite.)
5. Verify as in 9.1 (history version, counts, `die_app` privileges).
6. Point `DB_URL` (and credentials if changed) at it, start the API. Flyway applies migrations newer than the dump.
7. **Invalidate sessions** (section 10): rows in the dump can reference sessions of users whose passwords changed after the backup was taken.
8. Reconcile asynchronous work: outbox rows `PENDING` in the dump publish again (consumers dedupe); test jobs that finished after the backup time reappear as unfinished and are handled by the reaper. Tell affected users what happened between the backup time and the incident: that window is lost.
9. Run the smoke test.

Recovery objective you can honestly state today: **data loss up to the age of your newest off-platform dump** (plus whatever Supabase PITR adds, if enabled); recovery time is dominated by creating the project and restoring, typically under an hour for small datasets, *not measured*.

## 10. Session invalidation

Sessions are rows in `spring_session` (+ attributes, deleted by cascade). *(run)*

* **Everyone** (after a restore, a suspected leak, a role-model change): as the schema owner, `DELETE FROM spring_session;`. Verified: a logged-in admin's next `GET /api/v1/auth/me` returned 401. Users sign in again; nothing else is lost.
* **One user**: deactivate or reset credentials through the administrator API/UI (`POST /api/v1/users/{id}/deactivate` or `reset-credentials`), which revokes that user's sessions after commit. A password change or reset also revokes the other sessions of that user.
* The revalidation filter drops a session on the next request when its user was deactivated, deleted or had the role changed, even without the above.
* The CSRF cookie is not a secret of the server; there are no signing or encryption keys for sessions to rotate. If `DB_*`, SMTP or broker credentials leaked, rotate them (sections 5.4 and deployment.md) and invalidate sessions as well.

## 11. Incident quick reference

| Symptom | Look at | Likely cause | Action |
|---|---|---|---|
| Frontend loads but every call fails | `curl <frontend>/api/v1/status`; Render rewrite destination; API liveness | API down, or the `/api/*` rewrite points at the wrong host | fix the destination / restart the API |
| `/actuator/health/readiness` 503 | `GET /api/v1/ops/health` (ADMIN) or API logs (`broker health check failed`, `database health check failed`) | Postgres or RabbitMQ unreachable | follow the failing dependency; liveness stays UP on purpose |
| Jobs stay `QUEUED` | `outbox.pending`/`oldestPendingSeconds`, broker status | broker down (rows wait), relay error in logs | restore the broker; rows publish by themselves |
| Jobs stay `RUNNING`, then `FAILED` with "reaper" | worker states, DLQ depths (`dlq.py list`), worker logs by `correlationId` | worker down/stuck, poison message | restart worker, inspect DLQ, resubmit |
| `outbox.failed` > 0 | `last_error` column of the failed rows | broker refused the message (unroutable/nack) | fix topology/permissions, then `UPDATE outbox_event SET status='PENDING', attempts=0, next_attempt_at=now() WHERE status='FAILED' AND id='<id>'` as the owner |
| API will not start | log line `Refusing to start with unsafe configuration` lists every offending setting | production safety check | fix the listed variables (never work around it with the `local` profile) |
| Everybody locked out | audit log `LOGIN_FAILED`/throttle entries, `login_attempt` | lockout bucket shared behind a proxy (see deployment.md section 6) | wait 15 min or `DELETE FROM login_attempt` as the owner; fix forwarded-IP handling |
| Disk full on RabbitMQ | `rabbitmqctl list_queues name messages` | a stuck consumer or a DLQ nobody reads | read and clear the DLQ with section 5.2; enlarge the disk |

Trace one failure end to end: take the `traceId` shown in the error body (or the job's `correlationId`), search the API, orchestrator, document-worker and frontend logs for it, in that order of the data flow.
