# Document–Implementation Evaluator (DIE) — Master Project Brief v1.0 (controlled baseline)

Status: controlled implementation planning baseline. MVP = P0–P3. Supersedes `docs/brief-v0-original.md` (kept for history; where the two disagree, THIS file wins). Differences and open decisions: `docs/brief-reconciliation.md`.
Development approach: progressive, working end-to-end vertical slices. Inspect -> Implement -> Integrate -> Test -> Demonstrate -> Record evidence -> Accept -> Continue.

## 1. Overview
DIE is a web-based, AI-assisted platform for managing, submitting, evaluating, reviewing and approving software-development project documentation. Coordinators set up Project Workspaces, teams, SDLC workflows, requirements and artifact obligations. Participants prepare and submit documents from approved templates. Submissions get structural validation; an authorized Coordinator may start AI-assisted evaluation against rubrics/requirements. AI produces provisional, evidence-backed findings; Coordinators acting as reviewers accept/modify/reject/reconcile them; approved feedback is **explicitly published**; Participants may submit corrected versions. Version history, provenance, reviewer accountability, authorization boundaries and audit records are kept throughout.
**Implementation-code evaluation is NOT part of P0–P3.**

Objectives: secure accounts/roles; configurable Workspaces/Projects/teams; versioned requirements and SDLC workflows; document definitions, templates, policies, deadlines; DOCX upload + authorized Google Drive link import; structural validation and intake security; Drive storage; Coordinator-initiated AI evaluation; approved cloud/self-hosted models; evidence-grounded findings; independent human review, disagreement resolution, approval policies; explicit participant-safe publication; immutable artifact/evaluation/review/publication history; admin visibility into storage, AI providers, workers, health; delivery in verified vertical slices.

## 2. Roles (exactly three application roles)
| Role | Responsibilities |
|---|---|
| Project Participant | Assigned Workspaces/Projects, team participation, prepare/submit documents, view **published** feedback |
| Project Coordinator | Configure Workspaces, requirements, workflows, templates, teams, projects; manage submissions; initiate and review evaluations |
| Administrator | Accounts, storage config, AI providers, qualification, routing, infrastructure health, recovery |

- One active application role per account.
- Workspace Owner is a Coordinator responsibility, not a role. Reviewer / lead reviewer / final approver are workflow responsibilities assigned to eligible Coordinators. Multiple Coordinators may be assigned to a Workspace; every active Workspace has exactly one designated authorized Owner.
- Resource-level capabilities govern sensitive Coordinator operations.
- **Administrator authority does not automatically grant access to private project documents, reviewer decisions or approval operations.**
- Backend authorization is authoritative; the frontend only presents permission-aware controls.

## 3. MVP phases
**P0 Technical foundation:** React + Spring Boot connected; Supabase Postgres + Flyway; Spring Security + secure shared server-side sessions; containerized RabbitMQ; separate Java orchestration and Python worker containers; Docker Compose; Render Blueprint; env-specific config and protected secrets; health monitoring and integration smoke tests. *Done when everything runs together and is verified by real execution.*
**P1 Identity and Project Workspaces:** admin bootstrap and account management; Coordinator invitation/activation; Participant provisioning, roster import, duplicate reconciliation; login, activation, email verification, password establishment; Workspace creation/ownership/Coordinator assignment; Workspace Participant membership; individual/team Project formation with configurable min/max; role-specific dashboards, protected routes, Workspace/Project views. *Admin -> Coordinator -> Workspace -> Participant activation -> team/Project access works end to end.*
**P2 Requirements, SDLC workflow, document intake:** structured, versioned Requirements Sets (draft/validate/publish/explicit assignment); reusable configuration templates; SDLC workflow DAGs with progression rules; versioned artifact definitions and Coordinator-provided DOCX templates; secure direct upload + Google Drive link import; server-persisted drafts; structural validation (errors/warnings/corrections); Drive storage resolution; immutable submission versions and provenance; deadlines, extensions, revision requests (Blocking/Advisory); controlled requirements/workflow migration.
**P3 AI evaluation and human review:** numerical/qualitative rubrics; versioned provider/model registry; qualification and capability-specific routing; Coordinator-initiated eligibility-checked evaluation; durable jobs through RabbitMQ; Java orchestration + Python analysis; approved cloud/self-hosted execution; evidence-grounded findings preserving original AI output; assigned independent reviewers; accept/modify/reject and disagreement handling; configurable one- or multi-approver policy; final assessment approval; separate explicit publication; participant-safe findings and publication history; corrected documents/feedback revisions; operational retry, incident and recovery controls.

**Out of scope (post-P3):** GitHub/ZIP source ingestion and implementation verification; AI requirements extraction and lineage; document-vs-code conformance; cross-project analytics; broad notifications/campaigns; advanced backup/retention automation; Agile change-impact evaluation; advanced evidence exports/multi-document traceability; institutional SSO. The MVP still includes minimum security, audit, retention and recovery protections.

## 4. Approved stack
Frontend: React + Vite + TypeScript, Tailwind CSS, shadcn/ui, React Router, TanStack Query, React Hook Form + Zod. Backend: Java Spring Boot, Spring Security with secure cookie-based server-side sessions, versioned REST `/api/v1`, OpenAPI, SSE. DB: Supabase PostgreSQL + Flyway. Storage: Google Drive API behind a provider abstraction. Broker: RabbitMQ. Workers: Java orchestration worker + specialized Python workers. AI: qualified hybrid self-hosted and cloud providers. Docker, Docker Compose, Render Blueprint. Tests: Vitest + React Testing Library + MSW, Playwright, JUnit/Spring integration, pytest, real containerized services plus controlled provider acceptance.
Architecture: React -> HTTPS/REST/SSE -> Spring Boot API (auth + domain services) -> {Postgres, Google Drive, RabbitMQ}; RabbitMQ -> Java worker -> Python workers -> qualified AI models. The database is the authoritative business-state store; the broker delivers durable tasks; results and transitions are persisted through controlled backend contracts.
Backend domain modules (boundaries, not microservices): Identity and Access; Project Workspace Management; Project and Team Management; Requirements Management; SDLC Workflow Management; Artifact Management; Google Drive Storage Management; AI Evaluation Management; Human Review; Approval and Publication; AI Provider Administration; Operations and Recovery.
Frontend: single React app with role-aware nested layouts; public auth screens; Participant, Coordinator and Administrator dashboards/management screens; shared Project/Artifact components; permission-aware actions; responsive navigation; server-persisted drafts with conflict handling; contextual loading/validation/error/recovery states. Controlled registry of **60 canonical screen entries** under `SCR-AUTH`, `SCR-SYS`, `SCR-PAR`, `SCR-COO`, `SCR-ADM`.

## 5. Business rules
**Workspace/Project:** (1) every active Workspace has an authorized Owner; (2) multiple Coordinators may administer within delegated capabilities; (3) Participants may belong to several Workspaces when authorized; (4) at most one active Project membership per Participant per Workspace; (5) team min/max set by Coordinator; (6) Projects keep assigned requirements/workflow versions until explicitly migrated; (7) migration needs impact review, compatibility validation and authorized confirmation.
**Requirements/workflow:** (1) Requirements Sets have stable requirement identities; (2) published requirements/workflow versions are immutable; (3) Draft, Validate, Publish, Assign are distinct operations; (4) SDLC stage dependencies form a valid DAG; (5) progression obeys prerequisites and approvals; (6) historic stage completions survive migration; (7) drafts bound to earlier versions need adaptation/revalidation.
**Documents/storage:** (1) every artifact has a definition and submission policy; (2) approved DOCX templates are versioned; (3) authorized team members may submit; (4) structural validation precedes accepted submission; (5) unsafe/unauthorized documents are rejected; (6) drafts stay correctable, submitted versions are immutable; (7) **Drive destination precedence: Project override -> Workspace override -> Administrator default**; (8) configured-but-unavailable storage blocks, never silently falls back; (9) historical provenance stays with the original destination; (10) Drive link import requires authorized access, secure acquisition, integrity verification, safe parsing.
**AI evaluation:** (1) only an authorized Coordinator initiates; (2) artifact must meet validation and SDLC eligibility; (3) unresolved applicable Blocking revision requests prevent initiation; (4) providers/models need approved qualified capabilities; (5) each attempt records immutable artifact, model, configuration and evidence context; (6) provider fallback only between distinct execution attempts; (7) AI findings are provisional; (8) external provider data handling must satisfy approved security/retention policy; (9) worker retries bounded and auditable; (10) failed/stale attempts get controlled reconciliation and recovery.
**Review/approval/publication:** (1) review follows a configurable versioned review policy; (2) multiple reviewers may decide independently; (3) reviewer decisions stay independently attributable; (4) disagreements need explicit adjudication where applicable; (5) approval requires completed reviews and a satisfied configured quorum; (6) a designated authorized final authority finalizes; (7) publication is a separate authorization-controlled action; (8) Participants see only published findings; (9) published feedback belongs to a specific immutable artifact version; (10) corrections to publications create immutable revisions.
**Security/audit:** secure HttpOnly SameSite session cookies; CSRF on cookie-authenticated mutations; backend-enforced authorization; deny cross-Workspace/cross-Project access; protect Google OAuth credentials and AI provider secrets; **account security versions for session revocation**; protect immutable submission/evaluation/publication provenance; record privileged operations (actor, resource, outcome, correlation); minimum-necessary diagnostics; versioned retention and recovery policies.

## 7. Testing, release, governance
Every slice uses: unit tests for domain rules; React component/interaction tests; OpenAPI/DTO contract checks; real PostgreSQL + broker integration tests; security/authorization negatives; concurrency + idempotency; failure/retry/recovery; critical Playwright E2E; controlled Drive and AI live acceptance; deployment smoke/health. Mock-only success does not satisfy real-integration acceptance.
**Definition of Done:** all assigned requirements implemented or dispositioned; frontend works; backend + authorization work; db changes and state verified; external integrations work; positive and negative tests pass; critical E2E passes; release gates pass; no acceptance-blocking issue; git/CI/environment/verification evidence recorded.
Release: versioned Flyway checks; protected prod secrets; dependency + readiness verification; rollback-compatible deploys; controlled worker/queue recovery; alerts and incident history; evidence-backed sign-off; explicit risk acceptance for non-blocking issues. A started service alone is not acceptance.
Progress tracking per task: stable task/slice IDs, requirement + screen references, dependencies, owner, source revision, CI/test results, environment, risks/blockers, acceptance evidence. Status values: Not Started · In Progress · Blocked · Implemented — Unverified · Verification Failed · Accepted.
